# Bounding list sizes and string lengths (3.3 slice and 4.0 proposal)

**Status**: Draft for the working group. Follows WG Session C (2026-10-26), which decided to bound list sizes and string lengths across the protocol.

**Scope of this document**: an inventory of every unbounded array and string in `static/schemas/source/**`, a proposed limit for each, the 3.3 slice that bounds the fields allowed to change in a minor release, and the 4.0 plan for the rest. It is an internal proposal. The numbers are proposals until the owning working groups confirm them.

**Machine-readable companions** (all generated by `scripts/audit-schema-bounds.cjs`):

| File | What it holds |
|---|---|
| `scripts/schema-bounds-inventory.json` | The inventory of the tree as committed: one record per unbounded array or string, plus every inline property or collection list. |
| `scripts/schema-bounds-3-3-slice.json` | The bounds the 3.3 slice added, with the limit and tier for each. |

## The rule that shapes everything

A minor release only adds. The additive-minor check ([#8502](https://github.com/adcontextprotocol/adcp/pull/8502), `scripts/lint-additive-minor.cjs`) compares the schemas with the last stable release (3.2.7) and fails on a tightened bound, among other things. It exempts schemas marked `x-status: "experimental"`, and a field that did not exist in 3.2.7 has nothing to be compared with. So:

- A bound on a **stable** field that 3.2.7 already carries is a 4.0 change. This document proposes it and the v4 compatibility registry records it. No stable schema is edited.
- A bound on a field that is **new in 3.3** (never in a stable release) or **experimental** is allowed now. That is the 3.3 slice.

## Inventory

Counts are for the tree before the 3.3 slice. The WG discussed about 1,734 arrays in 460 files; main has since gained three experimental arrays (invoice lines, #8207).

Strings skipped as already constrained: `enum` (953), `const` (613), `format: date-time` (478), `format: date` (32), `format: email` (11), `format: uuid` (18), a bounded `pattern` (503), and a string that already has `maxLength` (430). A `pattern` is bounded when it is anchored at both ends and has no `*`, `+` or `{n,}`.

`format: uri` is skipped as the task rules say, but a URI has no length limit of its own. 306 such strings exist and 302 have no `maxLength`. They are listed in the inventory under `unbounded_uri_strings`. Recommendation: treat them like other URL-shaped values and bound them at 2,048 in 4.0.

How the columns are decided:

- **Side.** The script walks every `*-request.json` and every `*-response.json`, `*-async-response-*.json` and `*-webhook*.json` schema and follows `$ref`s. A node reached only from requests is *request*, only from responses (and webhooks, which are agent-to-agent pushes) is *response*, from both is *both*. A node reached from neither is *other*: documents such as `adagents.json`, `brand.json`, registry feeds, `compliance/` and `extensions/`. *Both* is mostly shared core types (`core/product.json`, assets, targeting).
- **Stability.** *Experimental*: the node or an ancestor in its file carries `x-status: "experimental"`. *New in 3.3*: not experimental, the node or an ancestor carries `x-added-in: "3.3.0"`, and 3.2.7 does not carry the same field on the wire. *Stable*: everything else.
- **"On the wire" is checked, not assumed.** Comparing a node with the same pointer in the same 3.2.7 file is not enough: 3.3 moved the relying-party object from `brand.json` into a new shared file. The new file is marked `x-added-in: "3.3.0"`, yet `relying_party_id` and `scheme` shipped in 3.2.7. The script therefore walks back from each candidate to every schema that references it, and asks whether 3.2.7 has the same path from the same root, following `$ref`s on both sides. Branch indexes are ignored, so an unclear match counts as released. The first run of the script without this check proposed two bounds that the additive-minor check rejected, which is how the case was found.
- **Markers that disagree with 3.2.7** (12 nodes) are treated as stable and left alone. They are either a stale `x-added-in` or a false match from the index-blind comparison. Follow-up for the owners:
  `core/product.json` and `core/canonical-product.json` `execution_requirements`; `core/wholesale-feed-event.json` `changed_fields` (array and items) and `summary`; `creative/sync-creatives-request.json` `assignment_operations` branch 3 `creative_id` and `package_id`; `media-buy/build-creative-response.json` both `errors` arrays; `core/identity-relying-party.json` `scheme` and `relying_party_id` (moved, shipped in 3.2.7); `protocol/get-adcp-capabilities-response.json` `supported_sections`.

## Proposed limits

Every record carries a tier, a limit and a one-line rationale. The tiers follow the numbers the schemas already use. Among bounded arrays, 100 is the ceiling on lists a caller sends (`creative_ids`, `media_buy_ids`, `task_ids`, `accounts`, `changes`), and 10,000 is the ceiling on `records` and `events`. Among bounded strings, 255 is the default for ids and names (262 fields), 2,000 for prose (41), 2,048 for URLs, and 4,096 for cursors and tokens.

| Tier | Limit | Applies to | Stable fields (4.0) |
|---|---:|---|---:|
| `array-enum` | max(32, enum size) | A set of enum values. The enum bounds it. | 336 |
| `array-small` | 32 | Attributes of one object: keys, identifiers, applied filters, closed vocabularies. | 177 |
| `array-typical` | 100 | Lists nested in an object; the default when no name signal exists. | 652 |
| `array-batch` | 100 request, 1,000 response | Request batches and id lists, and the response that echoes or pages them. | 165 |
| `array-large` | 1,000 | Id, domain and handle lists on a response that scale with an account or portfolio. | 60 |
| `array-catalog` | 10,000 | Records, events, rows, inline catalog items. | 4 |
| `string-code` | 64 (30 for phone) | Codes, versions, currencies, locales, short enums that are not closed. | 272 |
| `string-id` | 255 (200 street, 100 city) | Identifiers, names, labels. | 862 |
| `string-domain` | 253 | DNS names. RFC 1035. | 65 |
| `string-text` | 2,000 | Reasons, messages, descriptions. | 207 |
| `string-url` | 2,048 | URL-shaped values. | 11 |
| `string-token` | 4,096 | Cursors, tokens, signatures, consent strings. | 43 |
| `string-body` | 100,000 | Long bodies: asset `content`, `brief`, `preview_html`, video `prompt`. | 15 |
| `string-generic` | 500 | No name signal. Needs the owning group to confirm. | 399 |
| inline property list | none | See the next section. | 48 |

The large limits and why:

- **`array-catalog` 10,000.** `core/catalog.json` `items`, `registry-feed-response` `events`, `get-media-buy-delivery-response` `reporting_rows`, `get-property-list-response` `identifiers`. These are the only fields that legitimately carry catalog-scale data in one payload. 10,000 is the ceiling already used for `records` and `events`, and 10,000 small objects fit inside the 4 MiB response default (`security.mdx`). A catalog larger than that has `url` (and pagination), which is where it belongs. Treat 10,000 as the ceiling to argue about, not a target.
- **`array-large` 1,000.** Id lists a response may enumerate for an account: `media_buy_ids`, `package_ids`, `signal_refs`, `format_ids`, `placement_ids`, `collection_ids`. A seller with a large account has hundreds. On the request side the same lists get 100, to match the siblings already bounded at 100.
- **`string-body` 100,000.** The existing `content` (100,000) and `transcript` (200,000) bounds, applied to asset bodies (CSS, JavaScript, HTML, markdown, VAST, DAAST), briefs and preview markup. Anything bigger is an asset and belongs behind a URL; the 1 MiB `markup` ceiling already in the schemas covers the one place where inline markup must be larger.
- **`string-token` 4,096.** Matches the 4,096 already on `cursor`, `token` and `governance_context`. An IAB TCF consent string can reach a few KB, so it must not be bounded lower.

Rules of thumb behind the small ones: a list of more than 32 enum values, tags, keys or identifiers on one object is a modelling error; a list of more than 100 items inside a request body should be a paged read or a reference.

**Low-confidence limits.** 399 stable strings fall in `string-generic` (500) and most arrays in `array-typical` (100) were not matched by name. They are placeholders for the owning working group. Tightening is the risk, not loosening: a bound can later be raised in a minor release, and cannot be lowered.

## Property and collection lists are always out of band

The WG rule: a property or collection list is always passed by reference (`agent_url` + `list_id`, the shape of `property-list-ref.json` and `collection-list-ref.json`), never inline. The script flags every array that carries one inline, bounded or not, and gives it **no limit**. The 4.0 action is **move out of band**. 56 arrays, of which 55 are unbounded; 34 are property lists and 22 are collection lists.

By where the list sits:

**Request and response fields: these are the cases to move.**

| Field | Stability | Side |
|---|---|---|
| `core/product.json` `publisher_properties`, `collections` (and `core/canonical-product.json`) | stable | both / response |
| `core/placement-definition.json` `property_ids`, `property_tags` | stable | other |
| `core/collection-distribution.json` `property_ids` | stable | both |
| `core/publisher-property-selector.json` `publisher_domains`, `property_ids`, `property_tags` | stable | both |
| `core/collection-selection.json` `collections` | stable | both |
| `media-buy/get-products-response.json`, `list-products-response.json`, `refine-proposals-response.json`, `request-proposals-response.json`, `list-collections-response.json`, `brand/get-brand-identity-response.json` `collections` | experimental | response |
| `media-buy/list-collections-request.json` `collections` | experimental | request (already `maxItems: 100`) |
| `trusted-match/provider-registration.json` `properties` (property RIDs a provider serves) | experimental | other |
| `protocol/get-adcp-capabilities-response.json` `media_buy.portfolio.publisher_domains`, `signals.data_provider_domains` | stable | response (owned by #8198; already bounded by `x-adcp-validation`, #8243) |

**List authoring: sources that build a managed list.**

| Field | Stability |
|---|---|
| `property/create-property-list-request.json`, `update-property-list-request.json` `base_properties` | stable |
| `property/base-property-source.json` `property_ids`, `identifiers`, and the tag selectors | stable |
| `property/property-list-filters.json` `exclude_identifiers` | stable |
| `property/property-list.json` `base_properties` (the stored definition, returned on reads) | stable |
| `collection/create-collection-list-request.json`, `update-collection-list-request.json` `base_collections` | stable |
| `collection/base-collection-source.json` `identifiers`, `collection-list-filters.json` `exclude_distribution_ids`, `collection-list.json` `base_collections` | stable |

**Documents** (`adagents.json`, `brand.json`, `aao/agent-publishers.json`, `core/registry-event.json`): 23 arrays. Here the inline list is the publisher's declaration and is the source of truth, not a list passed between agents, so "by reference" does not apply in the same way. They are flagged and left for the WG to rule on, because 4.0 can still bound them (documents have their own byte caps, for example 2 MiB for `brand.json`).

Judgment calls:

- **Authoring needs a way in.** `create_property_list` has to receive the list from somewhere. The `publisher_domain` + `tags` and `property_ids` selectors are queries over adagents.json, but `identifiers` is a plain enumeration. Moving authoring out of band needs a fetch-by-URL or a selector-only form first. That is the WG's call, so the doc proposes no limit and does not pretend the rule is already met.
- **The resolved page of a list read by reference is not inline.** `get_property_list` `identifiers` and `get_collection_list` `collections` are the data plane of the reference mechanism and are bounded at 10,000 per page instead.
- **Experimental inline lists were not bounded in 3.3**, though they could be, because bounding them legitimises the inline shape the WG rule is removing. Seven are left unbounded: six `collections` responses and the TMP provider registration `properties`. The six experimental `collections` fields on responses are the cheapest to move: an experimental surface can change with six weeks' notice.
- **Not flagged:** `allowed_domains` and `allowed_external_domains` in asset requirements (an allow-list of script hosts, not a property list), `placement_refs` (placement references, not properties), `governance_domains` (a vocabulary), `task_types`.

## The 3.3 slice

658 bounds in 155 files, listed in `scripts/schema-bounds-3-3-slice.json`:

| Keyword | Experimental | New in 3.3 | Total |
|---|---:|---:|---:|
| `maxItems` | 230 | 30 | 260 |
| `maxLength` | 348 | 50 | 398 |

What it does not touch:

- no stable field (a node classified stable is never edited, including the 12 marker conflicts above);
- `protocol/get-adcp-capabilities-response.json` (owned by #8198): 28 arrays and 8 strings are in the inventory as `deferred (#8198)`;
- inline property and collection lists;
- no `required`, `additionalProperties`, enum or property changes; each edit inserts one keyword after `type`, so no object is opened, closed or extended.

**Safety against #8502.** The check compares with 3.2.7, exempts experimental schemas, and cannot compare a field 3.2.7 never carried. The slice was run through the merged `scripts/lint-additive-minor.cjs`: no new violation, and `scripts/lint-additive-minor-baseline.json` is unchanged. The same check also found the one mistake in an earlier draft of the script (the moved relying-party fields above), which is why the script now compares wire paths.

**What a 3.3 beta reader sees.** `3.3.0-beta.0` is published and carries the new-in-3.3 fields without bounds. Bounding them is not a break against any stable release, but a beta consumer that generated code from the beta schemas may see a tighter bound. The scope freeze is 2026-10-26, so after 3.3 GA these fields become stable and can no longer be tightened. This is the last chance. If the WG prefers not to tighten fields that a beta has published, drop the 30 `maxItems` and 50 `maxLength` marked new in 3.3 from the slice file and keep the experimental ones.

**A bound on an experimental field is a patch-level change** under the experimental notice contract (`docs/reference/versioning.mdx`). The changeset is `patch`.

## The 4.0 plan for stable fields

1. The 1,442 stable arrays and 1,874 stable strings stay as they are in 3.x. Nothing in this PR edits a stable schema.
2. The v4 compatibility registry has one entry, `schema_bounds_required_in_4_0`, and the migration guide has a section with the tier table, so an implementer sees the limits coming. It is a `new_requirement` and is not observable by a 3.x run (`observed_by.none`), because a 3.x agent is validated against 3.x schemas that carry no bound.
3. At the 4.0 cut, regenerate the inventory, have each working group confirm or change the limit for its fields (the `string-generic` and `array-typical` rows first), and apply the result in one change. The script's `--check-unreleased` mode then holds the line: it fails if an array or string new in 3.3 or experimental has no bound.
4. Property and collection lists move out of band in the same release, so the 25 stable inline arrays in request, response and list-authoring schemas leave them instead of gaining a limit. The 23 in documents wait for the WG's ruling (see above).
5. Optional interim for 3.x: the precedent in #8243 puts a structural bound in `x-adcp-validation`, graded by a storyboard in 3.x and enforced by the schema in 4.0, so no previously valid document becomes invalid. Worth it for fields that third parties write (the DoS vector #8197 closed for capabilities). Not done here.

## Open questions for the WG

1. **Beta-published fields.** Tighten the 80 new-in-3.3 bounds now, or leave them to 4.0 with the stable fields (see above).
2. **`format: uri` strings.** 302 unbounded. Bound at 2,048 in 4.0?
3. **Request id lists at 100 versus 1,000.** 100 matches the bounded siblings (`creative_ids`, `media_buy_ids`, `task_ids`). Buyers with large accounts will hit it and should paginate or use a list reference.
4. **Documents (`other` side).** `brand.json` and the other fetched documents have byte caps. Whether they also get item caps is a separate decision from the task payloads.
5. **Property list authoring.** What replaces `base_properties` and `identifiers` as the way to create a list when inline is not allowed.
6. **Markers.** The 12 `x-added-in` markers that disagree with 3.2.7.

## Re-running

```bash
node scripts/audit-schema-bounds.cjs                    # summary
node scripts/audit-schema-bounds.cjs --write            # regenerate scripts/schema-bounds-inventory.json
node scripts/audit-schema-bounds.cjs --check            # fail if the committed inventory is stale
node scripts/audit-schema-bounds.cjs --check-unreleased # fail if a new-in-3.3 or experimental array/string has no bound
```

`--check` and `--check-unreleased` are not wired into CI. Wiring `--check` makes every schema PR regenerate a 1.3 MB file; wiring `--check-unreleased` is the useful ratchet, because it makes every new 3.3 field arrive with a bound. `tests/audit-schema-bounds.test.cjs` covers the script on fixture trees and runs in `test:contracts`.
